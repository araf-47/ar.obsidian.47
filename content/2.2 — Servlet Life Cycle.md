Excellent. This is my favorite lesson in the Servlet module because it explains **why Servlets (and later JSPs) behave the way they do**.

By the end of this lesson, you'll understand something that many developers don't realize until much later:

> **Tomcat usually creates only ONE object of your Servlet and uses it to handle MANY requests.**

That single sentence has huge implications.

# What is a Life Cycle?

Let's forget Servlets for a minute.

Think about a human.

```text
Birth

↓

Childhood

↓

Adult

↓

Death
```

Everything goes through stages.

A butterfly.

```text
Egg

↓

Larva

↓

Pupa

↓

Butterfly
```

Even a Java object has a life cycle.

```text
Create Object

↓

Use Object

↓

Garbage Collected
```

A Servlet is no different.

It also has a life cycle.

# The Servlet Life Cycle

Here is the complete picture.

```text
Tomcat Starts

↓

Create Servlet Object

↓

init()

↓

Ready to Handle Requests

↓

doGet()/doPost()

↓

doGet()/doPost()

↓

doGet()/doPost()

↓

...

↓

Tomcat Stops

↓

destroy()
```

Notice something.

The Servlet is **not created for every request.**

This is the biggest idea in today's lesson.

# Step 1 — Constructor

Suppose your Servlet looks like this:

```java
public class StudentServlet extends HttpServlet {

    public StudentServlet() {
        System.out.println("Constructor called");
    }

}
```

When does this constructor run?

Only once.

When Tomcat creates the Servlet object.

Not for every request.

---

# Step 2 — `init()`

After creating the object:

Tomcat calls

```java
init()
```

Think of it as:

> "Prepare yourself."

Maybe your Servlet needs to:

* Open a database connection (not usually recommended directly in the Servlet, but it's a useful example)
* Read configuration
* Load a file
* Initialize some resources

This happens once.

```text
Create Object

↓

init()

↓

Ready
```

---

# Step 3 — Wait

Now the Servlet waits.

Nothing happens.

Until...

A browser sends a request.

---

# Step 4 — `service()`

This is an important method.

Every request first arrives here.

```text
Browser

↓

Tomcat

↓

service()
```

But here's the nice part.

Normally, **you don't override `service()`.**

`HttpServlet` already implements it.

Its job is to inspect the HTTP method.

For example:

```text
GET

↓

doGet()
```

or

```text
POST

↓

doPost()
```

Think of `service()` as a receptionist.

It looks at the request and decides which room to send it to.

```text
Request

↓

Receptionist (service)

↓

Correct Doctor

↓

doGet()

or

↓

doPost()
```

---

```

Tomcat:

↓

service()

↓

doGet()
```

# POST Request

Browser:

```http
POST /login
```

Tomcat:

```text
↓

service()

doPost()
```

Simple.

# Why Don't We Call `doGet()`?

This is an excellent question.

Some beginners think:

```java
StudentServlet servlet = new StudentServlet();

servlet.doGet(...);
```

No.

Remember Module 2.1.

Tomcat controls the Servlet.

Tomcat decides when `doGet()` runs.

Not you.

---

# Step 5 — Repeat

Suppose 1,000 people visit your website.

Does Tomcat create:

1,000 Servlets?

No.

Instead:

```text
One Servlet

↓

Request 1

↓

doGet()

↓

Request 2

↓

doGet()

↓

Request 3

↓

doGet()

↓

...

↓

Request 1000

↓

doGet()
```

One object.

Many requests.

This is very efficient.

---

# Step 6 — `destroy()`

Eventually:

You stop Tomcat.

```bash
./shutdown.sh
```

Tomcat says:

> Before I remove this Servlet...

```java
destroy()
```

This is the Servlet's opportunity to clean up.

Examples:

* Close files
* Release resources
* Save final state (if needed)

After that...

The Servlet object is removed.

# A Very Important Consequence

Remember:

Only one Servlet object usually exists.

Suppose you write:

```java
public class StudentServlet extends HttpServlet {

    int count = 0;

}
```

Now Alice visits.

```text
count = 1
```

Bob visits.

```text
count = 2
```

Charlie visits.

```text
count = 3
```

Everyone is sharing the **same Servlet object**.

This is why storing user-specific information in Servlet instance variables is usually a bad idea.

Later, we'll learn the proper places to store per-user data (such as the session).

For now, just remember the idea:

> **One Servlet object serves many requests.**

---

# How Does This Relate to JSP?

Remember what we learned:

```text
JSP

↓

Tomcat

↓

Generated Servlet
```

That generated Servlet follows the **same life cycle**.

So when you refresh a JSP page, Tomcat is generally **not** creating a brand-new Servlet each time.

The existing Servlet handles another request.

This connection is one of the main reasons we're learning Servlets before JSP.
